# 耀坤 S3 适配说明（`yaokun-organized` 分支）

> 本文记录 Flix **耀坤整理版**相对上游 `okalachev/flix` 的全部代码改动、每个改动的**根因分析**与**验证方法**。  
> 读完本文你应该能回答三个问题：改了什么、为什么必须改、怎么确认改对了。

- 上游：<https://github.com/okalachev/flix>（`(C) Oleg Kalachev`）
- 本分支：<https://github.com/YaoKunS/flix> 的 `yaokun-organized`
- 版本：**v1.0**
- 硬件：耀坤 S3 无人机（ESP32-S3，4MB Flash）
- 对照参考实现：2026-08 已验证可飞的 `flix20260819yaokun`

---

## 一、一句话结论

上游版本的 ESP-NOW 接收走的是"**会话式**"封装，而耀坤自研遥控器**不会发起会话**，  
所以遥控器显示已连接、飞机毫无反应。本版改用**原生 ESP-NOW 回调 + 字节队列**接管接收，  
同时把时间基准、IMU 识别、灯语、界面语言等一并修好，形成一块能直接飞的板子。

## 三、逐条根因分析

### R1 · 时间基准 32 位回绕（🔴 最隐蔽的坑）

**现象**：上电运行约 **71.6 分钟**后，遥测全部停发、串口终端仍在回显命令、`reboot` 后恢复正常。  
换个固件版本或重上电就"好了"，所以极难复现、极易被误判为"Wi-Fi 掉线"。

**根因**：

```cpp
// 上游写法
t = micros() / 1000000.0f;
```

`micros()` 在 ESP32 Arduino 上返回 **uint32**，最大 4294967295 µs ≈ **4294.97 秒 ≈ 71.58 分钟**，  
到顶后**回绕到 0**。于是 `t` 从 4294.97 突变到 0 —— **时间倒退**。

而全工程的门控都是这个形式：

```cpp
Rate telemetrySlow(2);
if (telemetrySlow) { ... }        // 内部是 t - lastTime >= 1/rate
```

`t - lastTime` 变成负数 → 判据永远不成立 → **所有周期性任务集体停摆**：遥测、日志、参数同步、  
灯语更新全部停。但 `handleConsole()` 是纯事件驱动（`Serial.available()`），不受影响，  
所以"终端还能敲命令"这个现象会把人往"Wi-Fi 问题"上带。

**修法**：用 64 位累加器把每次 `micros()` 的**增量**加起来，天然免疫回绕：

```cpp
static uint64_t timeUs = 0;
static uint32_t lastMicros = 0;
const uint32_t nowMicros = micros();
const uint32_t deltaUs = nowMicros - lastMicros;  // 无符号减法：回绕时也得到正确的增量
lastMicros = nowMicros;
timeUs += deltaUs;
t = timeUs / 1000000.0f;
```

`deltaUs` 用无符号减法，回绕瞬间（`nowMicros` 小、`lastMicros` 大）也能算出正确的正数增量 ——  
这是本修复的关键技巧。同时留了两个探针：

- `tRewinds`：回绕次数，`time` 命令可看
- `tRewindAt`：最近一次回绕时的时间戳

**为什么不能简单用 `esp_timer_get_time()`**：它返回 int64，确实不回绕，但会引入一个新依赖，  
且在 Gazebo 仿真环境里没有这个符号。累加器方案零依赖、仿真也能跑。

**验证**：`time` 命令看 `微秒计数器回绕次数`，若 > 0 而遥测正常，说明修复生效。

### R4 · ESP-NOW 收不到遥控数据（🔴 本次核心）
**现象**：换上游 2026-09 之后，耀坤自研 ESP-NOW 遥控器怎么连都"没反应"。  
遥控器端 UI 显示已连接（它收到了飞机广播的 `flix` 发现包或收到了飞机遥测），  
飞机端串口**没有任何报错**，就是不动。2026-08 版一切正常。

**根因**（读 `ESP32_NOW_Serial` 库源码确认）：  
上游接收写的是

```cpp
int len = espnow.read(buf, size);
```

`ESPNOWSerial` 是**会话式**的：它内部维护一张 peer 表，**只把已登记 peer 发来的数据交上来**。  
登记 peer 的唯一途径是收到 4 字节内容为 `"flix"` 的**发现包**（触发 `onNewPeer` 回调）。

而上游发发现包的地方长这样：

```cpp
// wifi.ino（上游）
static Rate discovery(1);
if (discovery && espnow.isEncrypted()) {     // ← 关键门控
    espnowBroadcast.write((const uint8_t *)"flix", 4);
}
```

**不加密就根本不广播发现包**。耀坤遥控器不加密 → 飞机不发发现包 → 遥控器不知道飞机存在 →  
不建立会话 → 飞机 `espnow.read()` 永远返回 0 → **摇杆数据一个字节都收不到**。

这就解释了为什么"遥控器显示已连接"：遥控器的"已连接"判据是**收到飞机的任何 ESP-NOW 帧**  
（飞机的遥测广播），而不是"双向会话建立"。所以两边状态显示完全对不上。

**修法**（沿用 2026-08 已验证的做法）：

1. 额外注册**原生**接收回调，把每个字节塞进 FreeRTOS 队列：

```cpp
static QueueHandle_t recvQueue = nullptr;

static void IRAM_ATTR onReceive(const esp_now_recv_info_t *info, const uint8_t *data, int len) {
    if (!espnowRecvInitialized) return;
    for (int i = 0; i < len; i++) {
        if (xQueueSendFromISR(recvQueue, &data[i], NULL) != pdTRUE) {
            lostPackets++;   // 队列满：丢字节并计数，绝不阻塞中断
        }
    }
}
```

1. `receiveWiFi()` 在 ESP-NOW 模式下**优先**从队列取字节：

```cpp
if (wifiMode == W_ESPNOW) {
    if (!espnowRecvInitialized || recvQueue == NULL) return 0;
    int i = 0;
    for (; i < len; i++) if (xQueueReceive(recvQueue, &buf[i], 0) != pdTRUE) break;
    return i;
}
```

1. 发现包改为**无条件广播**（去掉 `isEncrypted()` 门控），让标准 flix 代理也能发现本机。

**三个必须注意的细节**：

| 细节                        | 为什么                                                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **不能重新 `esp_now_init()`** | `ESPNOWSerial` 已经初始化过。再调一次返回 `ESP_ERR_ESPNOW_INTERNAL`，并把已有 peer 全清掉 —— 发送链路也跟着废了。只调 `esp_now_register_recv_cb()`。 |
| **队列元素是 1 字节，不是整帧**       | MAVLink 解析器是**流式**的（`mavlink_parse_char` 逐字节喂）。存字节等于把"网络接收"和"协议解析"解耦，半截帧不会被丢。                                      |
| **队列满必须丢，不能等**            | 回调跑在 Wi-Fi 任务上下文。若在此阻塞等待，会把整个 Wi-Fi 任务拖住 → 整机卡顿。宁可丢旧字节。                                                            |

**验证**：

- 开机日志出现 `ESP-NOW 原生接收已启用`
- `wifi` 命令看 `原生接收` = 1、`队列字节` 有波动
- `rc` 命令摇杆时 `原始通道` 数字跟着变
- `接收丢弃字节数`（对应 `lostPackets`）应几乎不涨；涨说明主机处理不过来

**信道**：ESP-NOW 必须两端**同信道**。**本版默认 `espnowChannel = 1`**（2026-10-18 实测修正，详见下节）。  
本版新增 `ch` 命令，不必改代码重编：

```
ch          → 信道：1
ch 6        → ESP-NOW 信道已设为 6（遥控器必须一致），重启后生效
```

### R4 补充 · 2026-10-18 台架实测：三个连环坑

> 这一节是**实物验证**才暴露出来的，纯静态审查发现不了。三个坑串联，任何一个没解开都表现为
> 「遥控器显示已连接、飞机毫无反应、无任何报错」——同一现象、三种根因。

#### 坑 1 · 信道默认值错了（6 → 1）

| 项 | 内容 |
| --- | --- |
| **现象** | 飞机 `wifi` 显示 `接收包数：0`，遥控器侧显示"已连接" |
| **根因** | 早期按**英文版**遥控器源码 `Control.hpp` 里的 `esp_wifi_set_channel(6)` 把默认值定成 6。但实际在用的**中文版遥控** `ESP32-DJI-Dev-Yaokun20260815` **完全没有调用** `esp_wifi_set_channel`，走 Wi-Fi 默认信道 **1**。飞机听 6、遥控发 1，物理层彻底错开。 |
| **迷惑点** | 遥控器"对端发现"页**仍能列出飞机** —— 因为扫描是跨信道的。所以"能看到设备"不等于"数据能通"。 |
| **修法** | `espnowChannel = 1`（以已确认可用的 `D:\YaoKunS\Flix-YaoKun\flix` 为准） |
| **换遥控器必做** | 两边信道必须对齐。英文版遥控器是 6，中文版是 1，用 `ch <1-13>` 改飞机端。 |

#### 坑 2 · 飞机端从未登记 peer，单播包全被丢弃

| 项 | 内容 |
| --- | --- |
| **现象** | 信道对齐后 `接收包数` 仍然是 0 |
| **根因** | ESP-NOW 的硬性规则：**只有登记在 peer 表里的 MAC 发来的包才会触发接收回调**，未登记的来源在驱动层就被丢弃，回调根本不进。中文版遥控 `connect(mac)` 之后所有摇杆数据都是**单播**给飞机 MAC，而飞机端只调了 `esp_now_register_recv_cb()`、**从不 `esp_now_add_peer()`** —— 单向通。 |
| **为什么 8 月版没事** | 8 月版遥控走广播（`FF:FF:FF:FF:FF:FF`），广播包不需要预登记 peer。 |
| **修法** | ① 预登记广播地址（发现阶段的包能进来）；② `onReceive` 里记录来源 MAC，主循环 `learnPeerIfNeeded()` 自动 `esp_now_add_peer()`（**回调里不能直接 add，会取 Wi-Fi 锁导致死锁**）。 |
| **验证** | 首次收到新对端时串口打印 `已登记新的 ESP-NOW 对端：30:76:F5:EF:FE:08` |

#### 坑 3 · 遥控器 `enabled` 默认 false，不使能就只发中位值

| 项 | 内容 |
| --- | --- |
| **现象** | `接收包数` 正常增长、`msgid=69` 正确、但 `rc` 摇杆值恒为 0.01 不动 |
| **根因** | 中文版遥控 `ControlService::_enabled{false}` **默认关闭**。关闭时 `pollImpl()` 里 `if (_enabled) { 采样摇杆 }` 不成立，但 `MANUAL_CONTROL` **照发**，只是四个轴全是中位（≈0）。所以"有包、有帧、就是没数据"。 |
| **操作** | **按遥控器的「左按钮（辅助按钮）」** → `onSecondaryButtonClick()` 里 `enabled(!enabled)` 取反。**界面上没有这个开关，是纯物理按键。** |
| **判读** | 使能后推杆，`rc` 的四轴数值立即跟随 |

#### 为此新增的诊断字段（`wifi` 命令）

排查这类问题不能只看"有没有报错"，必须能回答"包到底到哪一层了"。本版在 `wifi` 输出新增：

```
接收包数：737          ← ① 物理层收到几个 ESP-NOW 包（0 = 信道/没发/peer 没登记）
接收字节数：16933       ← ② 总字节数
最近发包方 MAC：30:76:F5:EF:FE:08   ← ③ 谁在发（应为遥控器 MAC）
已解析 MAVLink 帧数：737 ← ④ 能组成几帧（远小于包数 = 协议不匹配）
最近一帧消息 ID：69（MANUAL_CONTROL=69） ← ⑤ 发的是不是摇杆包（2=HEARTBEAT 说明没发摇杆）
最近一帧来源 sysid：127  ← ⑥ 遥控制式（耀坤 = 127；被 target 过滤时看这个）
MAVLink 链路在线：1
```

**判读流程**：

| 现象 | 结论 |
| --- | --- |
| 包数 = 0 | 物理层没通 → 查信道（坑 1）、遥控器是否使能后仍在发、peer 是否登记（坑 2） |
| 包数 > 0，帧数 = 0 | 收到了字节但组不成 MAVLink 帧 → 遥控器在 Raw 协议模式 |
| 帧数 > 0，msgid ≠ 69 | 遥控器只发了 HEARTBEAT，没发摇杆（未使能 / 不在控制页） |
| msgid = 69，rc 全 0 | 遥控器未使能（坑 3），或 target 与 `mavlinkSysId` 不匹配 |

**台架实测最终结果（1 号机，2026-10-18）**：

| 项目 | 结果 |
| --- | --- |
| 接收包数 / 帧数 | 7674 / 7674（100% 解析） |
| 消息 ID / 来源 sysid | 69 (MANUAL_CONTROL) / 127 ✓ |
| 油门量程 | **-0.603 ~ +1.000**（中位 +0.010）✓ **±1000 全量程，非 0~1000** |
| 解锁 | 油门最低位时 `解锁状态` 0 → 1 成功切换 ✓ |
| 摇杆响应 | 0.010 → 0.207 → -0.603 → +1.000 连续跟随 ✓ |

### R2 · 指令 ACK 缺失导致地面站卡死

**现象**：QGC 点"解锁"被拒绝时，界面一直转圈到超时；点"切换模式"遇非法参数同样卡住。

**根因**：上游在被拒绝的分支上直接 `return MAV_RESULT_DENIED`，虽然当前版本在  
`COMMAND_LONG` 分支里是"拿返回值再发 ACK"的写法，但历史版本曾经出现过漏发 ACK 的情况。  
更稳妥的做法是**结构上保证不可能漏**。

**修法**：`handleMavlinkCommand()` 只负责**决定结果码 + 做副作用**，绝不自己发 ACK；  
发 ACK 统一由调用方在函数返回后无条件执行：

```cpp
int result = handleMavlinkCommand(&m);
mavlink_message_t ack;
mavlink_msg_command_ack_pack(..., m.command, result, ...);
sendMessage(&ack);   // ← 无论 accepted / denied / unsupported 都发
```

被拒绝时同时通过控制台打印中文原因（`拒绝解锁：油门不在最低位` / `设置模式被拒绝：模式号无效`），  
现场不用接地面站也能知道为什么被拒。

**验证**：QGC 里油门推起后点解锁 → 立即返回"被拒绝"（而不是转圈），串口打印中文原因。

### R7 · IMU 型号错 → 空指针崩溃

**现象**：把 1 号机（MPU6050，I2C）的固件烧到 2 号机（MPU-6500，SPI）上，开机就崩。

**根因**：`FlixPeriph` 的 `IMU::create(model, bus)` 在型号/总线组合不受支持时返回 `nullptr`  
（例如 MPU6050 只能走 I2C）。上游 `setupIMU()` 拿到返回值后**不判空**就直接调  
`imu->begin()`、`readIMU()` 里直接 `imu->read(...)` → **空指针解引用**。

**修法**：

1. **上电自动识别**：裸读 WHO_AM_I 寄存器（0x75）判断实际芯片。

```cpp
// probeI2C()：用 Wire 扫 I2C 地址，读 0x75
// probeSPI()：对候选 CS 拉低后读 0x75
// WHO_AM_I 取值：0x70/0x68/0x72 → MPU6050 系；0x70/0x71/0x73/0x74/0x98/0x75 → MPU6500 系
```

1. **朝向按总线分档**（只认一个判据：**右侧压低 → `st.roll` 为正**）：

| 总线  | IMU      | `imuRotation`  | 说明                           |
| --- | -------- | -------------- | ---------------------------- |
| I2C | MPU6050  | `(0, 0, +π/2)` | 国产 6050 模块的贴片方向与 6500 差 180° |
| SPI | MPU-6500 | `(0, 0, −π/2)` |                              |

> ⚠️ **判据只认 `st.roll` 符号**，不能用 `imu` 命令里的原始加速度（原始值还带着安装误差）。  
> ⚠️ **换 IMU 必须重跑 `ca`**（加速度计六面校准），零偏与比例系数每个芯片都不一样。

1. **`imuOK` 防护**（这是防崩的关键）：

```cpp
if (imu == nullptr || imu->status() != 0) {
    imuOK = false;
    print(TXT_IMU_UNUSABLE);   // 惯性测量单元不可用 —— 已禁止解锁（请检查排母/接线）
    return;
}
```

```cpp
void readIMU() {
    if (!imuOK || imu == nullptr) return;   // ← 首行就挡掉
    ...
}
```

IMU 不可用时，`setup()` 里**红灯常亮 + 长鸣 700ms**，让现场一眼看出不是"设置问题"。

**验证**：串口第一屏应出现

```
正在自动识别惯性测量单元…
  识别为 MPU-6500 系（SPI）SCK=38 MISO=21 MOSI=18 CS=17
  芯片标识（WHO_AM_I）= 0x70
  安装朝向补偿：绕 Z 轴 -1.5708 弧度  [按总线分档]
惯性测量单元就绪：MPU6500，总线 SPI
```

#### R7 补充 · 新旧 PCB 自动兼容 + I2C 全总线扫描（2026-10-18 台架实测）

**需求**：耀坤有两版 PCB —— V1（老板，机架已在用）与 V2（按《耀坤S3无人机引脚定义.xlsx》改线）。
要求**同一份固件、不重编**就能都跑。

| 信号 | V1 老板（实测） | V2 新板（引脚定义表） | 处理方式 |
| --- | --- | --- | --- |
| MPU6500 SCK / MISO / MOSI | 38 / 21 / 18 | 38 / 21 / 18 | 相同，固定 |
| **MPU6500 CS** | **GPIO17** | **GPIO42** | 候选表 `{imuCsPin, 42, 17}` 依次探测 |
| MPU6500 INT | GPIO17（与 CS 复用） | GPIO40 | **本工程不用**（定时器采样，非中断） |
| MPU6050 SDA / SCL | GPIO9 / GPIO8 | GPIO9 / GPIO8 | 相同，固定 |

> ⚠️ V2 表里写的是 `MPU6500_CS = GPIO42`、`MPU6500_INT = GPIO40`；V1 老板实测 CS 落在 17。
> 候选表把两者都试一遍，谁读到合法 `WHO_AM_I`（0x70/0x71/0x73）就用谁 —— 两版板子零配置自适应。

**I2C 侧：从"固定地址"升级为"全总线扫描"**

原实现只探 `0x68` / `0x69`（AD0 决定的"标准"地址）。台架实测发现：耀坤采购的部分 MPU6050 模块
**丝印/资料标注非标地址**，固定探测表会漏。改为扫描 `0x08~0x77` 全段：

```cpp
for (uint8_t addr = 0x08; addr <= 0x77; addr++) {
    Wire.beginTransmission(addr);
    if (Wire.endTransmission() != 0) continue;   // 无 ACK，跳过
    // 有 ACK：读 WHO_AM_I(0x75)
    //   合法 MPU id → 直接采用
    //   非法 id    → 记为兜底候选（可能是识别表外的国产兼容片）
}
```

**判据**：`0x68`/`0x69` 优先级最高（标准地址最可信）；其余按地址升序。
若全程没有合法 id 但有地址应答，则用第一个应答地址兜底，并按 6050 系（model=3）尝试 ——
`setupIMU()` 里 `begin()` 失败还会自动换型号重试，不会死在探测阶段。

**台架实测结果（两台同时验证，同一份固件）**：

| 机器 | 板卡 | IMU 模块 | 识别结果 |
| --- | --- | --- | --- |
| 1 号机 | 立创 ESP32-S3 R8N8（COM28） | MPU6500（SPI） | `MPU-6500 / SPI / WHO=0x70 / CS=17 / 朝向 −π/2` ✓ |
| 2 号机 | 淘宝 ESP32-S3 N16R8（COM24） | MPU6050（I2C，非标地址） | `MPU6050 / I2C0 / WHO=0x68 / SDA=9 SCL=8 / 朝向 +π/2` ✓ |

> 🔴 **踩坑记录**：曾把 I2C 引脚按错误记忆写成 `SDA=8 / SCL=9`（与引脚定义表相反）。
> 1 号机插 SPI 模块不经过 I2C，所以完全没暴露；2 号机插 I2C 模块就永远探不到。
> **引脚表与实际冲突时以实测为准，但这次实测证明表格是对的 —— `SDA=9 / SCL=8`。**

### R8 · 灯语与蜂鸣器（连接判据的坑）

**灯语优先级**（高 → 低）：

| 优先级 | 条件         | 表现                     |
| --- | ---------- | ---------------------- |
| 1   | 电压 < 3.5 V | 红灯 100 ms 快闪 + 蜂鸣器连续急鸣 |
| 2   | 已连接 且 已解锁  | 绿灯 200 ms 快闪           |
| 3   | 已连接 且 未解锁  | 绿灯常亮                   |
| 4   | 未连接        | 红灯 500 ms 慢闪           |
| 5   | 初始化中       | 蓝灯常亮（`setup()` 直接控制）   |

**音效语义**（与耀坤自研飞控 YaoKunDrone 保持一致，用户不用重新学）：

| 音效         | 触发             | 含义      |
| ---------- | -------------- | ------- |
| 短鸣 `'S'`   | 上电             | 开始初始化   |
| 双短鸣 `'D'`  | 初始化完成 / 遥控连上   | 就绪      |
| 三短鸣 `'T'`  | 解锁成功           | 已解锁     |
| 长鸣 `'L'`   | 失去遥控 / IMU 不可用 | 告警      |
| 连续急鸣 `'C'` | 低电量            | 循环到电压恢复 |

**🔴 连接判据的坑（必读）**：上游的语义等价写法是用 `mavlinkTime` 判断"地面站在线"，但  
`mavlinkTime` **任何** MAVLink 帧到达都会刷新 —— 包括地面站心跳、参数请求、  
甚至飞机自己发出的帧被回环计数。结果就是"**没接遥控也显示已连接**"，灯语在骗人。

本版改用 `controlTime`：

```cpp
const bool connected = valid(controlTime) && (t - controlTime < 1.0f);
```

`controlTime` **只在 `MANUAL_CONTROL`（遥控摇杆帧）到达时更新**，语义上才是真正的"遥控在线"。  
若启用了 SBUS，`readRC()` 也会更新它，两条路径都对。

**为什么蜂鸣器必须非阻塞**：如果在主循环里 `delay()` 放音，1 kHz 的主循环会被直接打断，  
姿态解算跟着丢步 ⇒ 解锁瞬间就翻。所以这里用"状态机 + 由主循环驱动"：

- `buzzerPlay(char)` 只设参数，立即返回
- `buzzerUpdate()` 在主循环里推进时序（`updateLED()` 第一件事就是调它）
- 只有 `setup()` 里那两次提示音用 `runBuzzerFor(ms)` 主动跑一小段（此时还没解锁，阻塞无害）

### R9 · 全中文界面（`i18n.h`）

**设计**：所有界面文字集中在 `Firmware/flix/i18n.h`，用 `TXT_*` 宏，`#ifdef FLIX_LANG_EN` 分中英两段。  
默认中文，编英文版只要在 `flix.ino` 最顶部加一行 `#define FLIX_LANG_EN`。

**为什么单独开文件而不是把中文分散写进各 `.ino`**：

1. 要保留"能编英文固件"的路（GPL 开源仓给海外用户）。若中文写死在 30 多个 `print()` 里，  
   切英文得逐行改代码 —— 极易漏改、diff 噪音巨大。
2. 文案集中后，"检查界面是否还有英文残留"变成**可脚本化**的事：确认所有 `print()` 都走 `TXT_*` 即可。
3. 将来串口屏 / 网页要复用同一套文案，只需包含这个文件。

**约定**：宏展开后是**字符串字面量**，所以写 `print(TXT_XXX)`，  
带参数的写成"前缀宏 + 格式串"两段拼接，保证中英文各自语序自然：

```cpp
print(TXT_CH_SET, ch);           // 前缀宏自带 %d
print(TXT_PWM_SET " %d\n", freq);
```

**校验**：`i18n.h` 中英文段各 **135** 条宏，脚本比对确认无单边缺失（`-- 仅英文段有` / `仅中文段有` 均为空）。

> ⚠️ **编码要求**：`i18n.h` 必须存为 **UTF-8 无 BOM**。若被记事本存成 GBK，  
> 中文会变成乱码字节直接发到串口。

### 第二级 · 台架验证（**必须拆桨**）


| 步骤 | 命令 / 操作          | 期望结果                               |
| -- | ---------------- | ---------------------------------- |

| 4  | `st` 倾斜机身        | 右侧压低 → `横滚` 为正（**这是朝向唯一判据**）       |
| 5  | 遥控器开机，`rc`       | `原始通道` 数字随摇杆变化；`最后收到遥控的时刻` 持续刷新    |
| 6  | `ch`             | `ESP-NOW 信道：6`（须与遥控器一致）            |
| 7  | `wifi`           | `原生接收` = 1；`接收丢弃字节数` 几乎不涨          |
| 8  | 摇杆到底 / 中位 / 到顶   | 油门归一化应为 **-1 / 0 / +1**（见下方"量程语义"） |
| 9  | `mfr 0.1` 逐个试电机  | 转向、位置对应正确（**务必拆桨**）                |
| 10 | `arm` / `disarm` | 三短鸣解锁 / 灯语切绿闪                      |
| 11 | 断开遥控器电源          | 1 秒后长鸣 + 红灯慢闪                      |

**⚠️ MANUAL_CONTROL 量程语义（台架必查）**：  
协议规定 `x/y/z/r` 是 int16，满量程 **±1000**。本工程 `controlThrottle = m.z / 1000.0f`，  
即 z 为 **-1000 ~ +1000**，中位 = 0。  
→ 若遥控器实际发的是 **0 ~ 1000**（中位当 0），则摇杆中位就已经是 0 油门、上半程才有推力，  
表现为"行程只有一半、且中点起跳"。**首次台架必须确认：最低杆 → z≈-1000，中位 → z≈0，最高杆 → z≈+1000。**

### 第三级 · 系留低飞

1. 装保护圈，系留绳固定，空旷场地
2. `arm` 解锁，缓慢推油门离地 10~20 cm
3. 轻点横滚/俯仰，确认**修正方向正确**（右倾 → 飞机向右修正）
4. 松杆，确认姿态回平（但**会继续水平飘** —— 这是正常的，无位置传感器）
5. 全程确认灯语：绿闪 = 已解锁，红灯闪 = 失联，红灯快闪 = 低电

## 五、已知限制

| 限制             | 说明                                             |
| -------------- | ---------------------------------------------- |
| **无定高**        | 没有气压计/测距，松油门就掉高度                               |
| **无定位**        | 没有 GPS/光流，松杆不悬停，会保持水平速度继续飘                     |
| **无自动降落**      | 只有 `rcLossFailsafe`（失联 1s 降油门、10s 归零上锁），不是定点降落 |
| **单 app 分区**   | `PartitionScheme=default` 无 OTA，升级只能插线重刷       |
| **控制台走原生 USB** | `CDCOnBoot=cdc`，只插板上 UART 口看不到日志               |
| **两机同开互相干扰**   | 同信道 ESP-NOW + 同名 AP，测试时另一台必须断电                 |

## 六、排查速查表

| 现象              | 最可能原因                    | 怎么确认                          |
| --------------- | ------------------------ | ----------------------------- |
| 遥控器显示连接、飞机不动    | ESP-NOW 信道不一致 / 原生接收未注册  | `ch` 看信道；`wifi` 看 `原生接收` 是否 1 |
| 遥控器显示连接、飞机不动    | 遥控器发 0~1000 而非 ±1000     | `rc` 看油门归一化值域                 |
| 上电 71.6 分钟后遥测全停 | R1 未生效（烧了旧固件）            | `time` 看 `回绕次数`；核对 SHA-256    |
| 开机红灯常亮 + 长鸣     | IMU 识别失败                 | `imu` 看 `识别依据` 与引脚            |
| 开机就崩 / 重启       | 烧错板型固件（IMU 型号不匹配）        | 看首屏 `识别为 …` 是否与实际芯片一致         |

| 手机连上就掉、界面假死     | 路由与飞机 AP 同信道             | 用 `ch` 错开，遥控器端同步改             |
