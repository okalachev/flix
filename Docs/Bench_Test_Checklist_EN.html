Pitfall 1: ESP-NOW mode also brings up a hotspot. ESP-NOW can only run on an AP/STA interface, so the moment WiFi.mode(WIFI_AP) is called the core starts a default hotspot named ESP_ plus the last three MAC bytes. Older builds only overrode the W_AP branch, so in ESP-NOW mode the aircraft broadcast the core default name and nobody could tell whose aircraft it was on site. Both paths must call WiFi.softAP(), and it must come after mode(WIFI_AP) — otherwise the mode switch wipes it.

Pitfall 2: the hotspot suffix must read the eFuse STA MAC (fixed in v1.1). Older builds used WiFi.macAddress(), which in AP / ESP-NOW context returns the AP interface MAC: aircraft #1 shows 本机 MAC：80:65:99:DF:F2:24 (STA) in wifi, while its AP MAC ends in 62:02, so the hotspot became YaoKun_6202 and no longer matched the wifi output — you could not identify the aircraft by MAC on site. It now reads the fuse directly via esp_read_mac(ESP_MAC_WIFI_STA) → always YaoKun_F224, so the last four hex digits of the MAC printed by wifi now reliably map to the hotspot name.

Pitfall 3: a placeholder hotspot name can be sitting in NVS. On aircraft #1 the NVS key WIFI_AP_SSID literally contained "<ssid>" (someone typed the documented placeholder straight into ap <ssid> <passphrase> back then), so auto-naming was skipped and the hotspot was really called <ssid>. v1.1 adds validation: a name containing < > or longer than 32 characters is treated as dirty data, cleared automatically, and auto-naming is restored.

🔴 Real bug: help prints only the brand bar, the command menu disappears

It is not "the menu was never written", it is truncated output. Three things have to line up:

  1. motd is one C string of 1718 bytes (brand bar + 30 command lines), emitted in a single Serial.print(buf);
  2. The ESP32-S3 native USB path uses HWCDC, whose TX ring buffer is only 256 bytes by default (setTxBufferSize(256) in the core's HWCDC.cpp);
  3. This project sets setTxTimeoutMs(0), so xRingbufferSend inside HWCDC::write() uses a 0-tick timeout and whatever does not fit is silently dropped on the spot.

⇒ Only the first ~256 bytes make it into the buffer, and the cut happens to land exactly at the end of the brand bar, so it looks like "the menu is missing" rather than "printing stopped mid-line".

Fix (console.ino, two parts working together):

  • setupConsole() now calls Serial.setTxBufferSize(4096), so the whole motd fits in one go; the USB interrupt drains it asynchronously and the main loop stays non-blocking;
  • handleConsole() ends each command with consoleFlushTail(150, ' ') — writing one extra space re-arms the USB interrupt and carries the stranded tail out.

Warnings from this fix:

  • ❌ Do not use Serial.flush(): with setTxTimeoutMs(0) it calls flushTXBuffer(NULL, 0), which discards the entire TX buffer and marks the port as not connected;
  • ❌ Do not write the drain test as >= 4096: the TX ring buffer is BYTEBUF, so the maximum free space is "capacity − 1" and that condition is never true.

1. Correct remote operation (★ most commonly missed)

Confirmed by testing: the Chinese remote does not enable control output by default; until it is enabled it only sends centre values. Full procedure:

  1. Power on the remote.
  2. Open the "peer discovery" page and wait for the aircraft to appear in the list (scanning crosses channels — seeing it does not mean reaching it).
  3. Tap that aircraft → establish the link.
  4. Press the left (auxiliary) button → enables control output (enabled = !enabled).

⚠️ There is no such switch in the UI — it is a physical button. One press on, one press off.

⚠️ After the aircraft reboots you must reconnect and press it again (the ESP-NOW session is gone).

Channels must match

RemoteChannel
Chinese (ESP32-DJI-Dev-Yaokun20260815)1 (Wi-Fi default, never set in code)
English (ESP32-YKRC-Firmware)6 (esp_wifi_set_channel(6) in Control.hpp)

The firmware defaults to espnowChannel = 1. When swapping remotes, change the aircraft side with ch <1-13>:

> ch          → 信道：1        (channel: 1)
> ch 6        → ESP-NOW 信道已设为 6（遥控器必须一致），重启后生效
              (channel set to 6 — the remote must match; takes effect after reboot)

7. Motors and arming

> mfr 0.1   → 右前  front-right    > mfl 0.1  → 左前  front-left
> mrr 0.1   → 右后  rear-right     > mrl 0.1  → 左后  rear-left
  • All four motors spin, position mapping correct (the one that spins for mfr really is the front-right motor)
  • Rotation direction matches the X-quad layout
  • mot shows all four channels at 0 with the throttle down

Arming:

  • Throttle to minimum → arm or arm from the remote → rc reports 解锁状态 (armed state) = 1
  • Three short beeps + green LED blink
  • Trying arm with the throttle off the bottom → prints "拒绝解锁：油门不在最低位" (arming refused: throttle not at minimum)

8. RC-loss failsafe

  • Pull the remote's power
  • Continuous tone + slow red blink within 1 second
  • After 10 seconds the throttle goes to zero and the aircraft disarms itself
