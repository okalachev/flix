一、项目定位

Flix 是一款专为教育与科研设计的开源四轴飞控固件，全部用 Arduino C/C++ 写成，不足 2000 行。没有 RTOS、没有闭源库、没有黑盒算法 —— 传感器驱动、姿态解算、PID 控制、电机混控、MAVLink 通信全部摊开在源码里。

本项目是 Flix 的耀坤 S3 硬件适配版：把上游固件跑到了耀坤自研的四轴机架上，并解决了"换用自研 ESP-NOW 遥控后飞机毫无反应"这一关键问题。

保持上游的结构

文件划分、主循环顺序、PID 结构、MAVLink 实现全部沿用上游。改的是硬件参数、接收链路与界面语言，不是重写内核。

分支说明

master 与上游 sha 完全一致，可随时 fast-forward 同步。yaokun-organized 才是带适配的分支。

GPL 义务：flix 上游没有独立 LICENSE 文件，版权归原作者 Oleg Kalachev。本仓库保留其署名与仓库地址，耀坤信息追加在其后。不要擅自标注其它协议。

3.2 主循环顺序（不要随意调整）

↓

↓
3readRC()SBUS 输入（ESP-NOW 输入在 processMavlink 里）
↓

↓

↓
6sendMotors()输出 PWM，越早越好，减少控制延迟
↓

↓

↓

不要把通信挪到 sendMotors() 之前。Wi-Fi / ESP-NOW 的收发在个别时刻会占用几毫秒，一旦排在电机输出之前，PWM 就会抖动，PID 表现为高频抖动甚至诱发振荡。这个顺序是从上游继承的，有其道理。

四、ESP-NOW 接收改造（本次核心）

4.1 现象

把上游 2026-09 的代码烧到飞机上后，耀坤自研 ESP-NOW 遥控器怎么连都"没反应"：

  • 遥控器端界面显示已连接
  • 飞机端串口没有任何报错
  • 摇杆推到底，飞机纹丝不动
  • 而 2026-08 版的代码一切正常

4.2 根因（读库源码确认）

上游接收写的是：

int len = espnow.read(buf, size);

ESPNOWSerial 是会话式的封装：它内部维护一张 peer 表，只把已登记 peer 发来的数据交上来。登记 peer 的唯一途径，是收到 4 字节内容为 "flix" 的发现包（触发 onNewPeer 回调）。

而上游发发现包的代码长这样：

// wifi.ino（上游）
static Rate discovery(1);
if (discovery && espnow.isEncrypted()) {   // ← 关键门控
    espnowBroadcast.write((const uint8_t *)"flix", 4);
}

不加密就根本不广播发现包。耀坤遥控器不加密 → 飞机不发发现包 → 遥控器不知道飞机存在 → 不建立会话 → 飞机 espnow.read() 永远返回 0 → 摇杆数据一个字节都收不到。

为什么"遥控器显示已连接"却不通？
遥控器的"已连接"判据是收到了飞机的任何 ESP-NOW 帧（比如飞机的遥测广播），而不是"双向会话已建立"。所以两边的状态显示完全对不上 —— 这也是这个问题最难查的地方。

4.3 修法

1
注册原生接收回调绕过会话机制，直接拿每一帧原始字节。
static QueueHandle_t recvQueue = nullptr;

static void IRAM_ATTR onReceive(const esp_now_recv_info_t *info,
                                const uint8_t *data, int len) {
    if (!espnowRecvInitialized) return;
    for (int i = 0; i < len; i++) {
        if (xQueueSendFromISR(recvQueue, &data[i], NULL) != pdTRUE) {
            lostPackets++;   // 队列满：丢字节并计数，绝不阻塞中断
        }
    }
}
2
接收路径改从队列取ESP-NOW 模式下优先走队列，队列空才返回 0。
int receiveWiFi(uint8_t *buf, int len) {
    if (wifiMode == W_ESPNOW) {
        if (!espnowRecvInitialized || recvQueue == NULL) return 0;
        int i = 0;
        for (; i < len; i++)
            if (xQueueReceive(recvQueue, &buf[i], 0) != pdTRUE) break;
        return i;
    }
    ...
}
3
发现包无条件广播去掉 isEncrypted() 门控，标准 flix 代理也能发现本机。

4.4 三个必须注意的细节

细节为什么
不能重新 esp_now_init()ESPNOWSerial 已经初始化过。再调一次返回 ESP_ERR_ESPNOW_INTERNAL，并把已有 peer 全清掉 —— 发送链路也跟着废了。只能调 esp_now_register_recv_cb()。
队列元素是 1 字节，不是整帧MAVLink 解析器是流式的（mavlink_parse_char 逐字节喂）。存字节等于把"网络接收"和"协议解析"解耦，半截帧不会被丢。
队列满必须丢，不能等回调跑在 Wi-Fi 任务上下文。若在此阻塞等待会把整个 Wi-Fi 任务拖住 → 整机卡顿。宁可丢旧字节。

4.5 信道：最容易漏的一环

ESP-NOW 必须两端同信道。信道不同时物理层直接收不到，现象是"连着但不动"且没有任何日志。

耀坤整理版默认 espnowChannel = 1，不是 6。这是一次实测纠错的结论：

⚠️ 2026-10-18 台架实测：信道 6 → 1
早期按"耀坤英文版遥控器里 esp_wifi_set_channel(6)"把默认值定成 6，但中文版遥控 ESP32-DJI-Dev-Yaokun20260815 完全没有调 esp_wifi_set_channel， 走的是 Wi-Fi 默认信道 1。于是飞机听 6、遥控发 1，物理层彻底错开。

这个故障极具迷惑性：遥控器"对端发现"页仍能列出飞机（扫描是跨信道的）， 点选后也显示"已连接"，但飞机 rxPackets 恒为 0。"能看到" ≠ "能通"。 
ch          → ESP-NOW 信道：1
ch 6        → ESP-NOW 信道已设为 6（遥控器必须一致）
ch 11       → ESP-NOW 信道已设为 11（遥控器必须一致）
              以上重启后生效

4.6 ESP-NOW peer 登记：第二个必踩的坑

ESP-NOW 的接收回调只对已登记在 peer 表里的 MAC 触发，未登记的设备发来的包在驱动层就被丢弃， 连回调都进不去。

遥控器发送方式飞机端是否需要预登记 peer
广播（FF:FF:FF:FF:FF:FF）❌ 不需要
单播（指定目标 MAC）✅ 必须登记，否则全部丢弃
⚠️ 2026-10-18 台架实测：中文版遥控 connect(mac) 后走单播
8 月那版遥控走广播，所以飞机端从不登记 peer 也没事；换中文版遥控后单向不通，rxPackets 恒为 0。

修法（wifi.ino）：
① 初始化时预登记广播地址为 peer；
② onReceive 回调里记录来源 MAC，置 peerLearnPending 标志；
③ 主循环 learnPeerIfNeeded() 里真正调用 esp_now_add_peer()。

🔴 为什么不在回调里直接 add_peer：esp_now_add_peer() 要取 Wi-Fi 锁， 而回调本身就跑在 Wi-Fi 任务上下文里 —— 直接调用会自锁死，整机卡住。

4.7 遥控器侧：enabled 开关（第三个坑）

⚠️ 中文版遥控 enabled 默认是 false
未使能时，遥控器 MANUAL_CONTROL 照发不误，但四轴数值全是中位（≈0.01）。 表现为："有包、有帧、msgid=69、sysid=127，rc 就是不动"。

使能方法 = 按遥控器的「左按钮（辅助按钮）」（代码里是 onSecondaryButtonClick → enabled(!enabled)）。界面上没有这个开关，是一个纯物理按键。

⚠️ 飞机每次重启，都必须重新走一遍：对端发现 → 点选飞机 → 按左按钮使能。

五、时间基准修复：71.6 分钟之谜

5.1 现象

上电运行约 71.6 分钟后，遥测全部停发、串口终端仍在回显命令、reboot 后恢复正常。换个固件或重新上电就"好了"，所以极难复现、极易被误判为 Wi-Fi 掉线。

5.2 根因

// 上游写法
t = micros() / 1000000.0f;

micros() 在 ESP32 Arduino 上返回 uint32，最大 4294967295 µs ≈ 4294.97 秒 ≈ 71.58 分钟，到顶后回绕到 0。于是 t 从 4294.97 突变到 0 —— 时间倒退。

而全工程的门控都是这个形式：

Rate telemetrySlow(2);
if (telemetrySlow) { ... }   // 内部判 t - lastTime >= 1/rate

t - lastTime 变成负数 → 判据永远不成立 → 所有周期性任务集体停摆：遥测、日志、参数同步、灯语更新全部停。

但 handleConsole() 不受影响 —— 它是纯事件驱动（Serial.available()）。所以"终端还能敲命令"这个现象，会把人死死地往"Wi-Fi 问题"上带，这也是本 bug 长期潜伏的原因。

5.3 修法

static uint64_t timeUs = 0;
static uint32_t lastMicros = 0;

const uint32_t nowMicros = micros();
const uint32_t deltaUs = nowMicros - lastMicros;  // 无符号减法：回绕时也得到正确增量
lastMicros = nowMicros;
timeUs += deltaUs;
t = timeUs / 1000000.0f;
关键技巧：deltaUs 用无符号减法。回绕瞬间（nowMicros 小、lastMicros 大），无符号减法会自动补模，仍然算出正确的正数增量。这就是"64 位累加器免疫回绕"的原理。

同时留了两个探针：tRewinds（回绕次数）与 tRewindAt（最近回绕时刻），用 time 命令可看。

5.4 为什么不用 esp_timer_get_time()

它返回 int64 确实不回绕，但会引入新依赖，且 Gazebo 仿真环境里没有这个符号。累加器方案零依赖、仿真也能跑。

六、IMU 自动识别

6.1 为什么要自动识别

FlixPeriph 的 IMU::create(model, bus) 在型号/总线组合不受支持时返回 nullptr（例如 MPU6050 只能走 I2C）。上游拿到返回值后不判空就直接调 imu->begin()、readIMU() 里直接 imu->read() —— 空指针解引用。

表现：把 1 号机（I2C 6050）的固件烧到 2 号机（SPI 6500）上，开机就崩，串口只打出半行。

6.2 识别流程

①probeI2C(0x68 / 0x69)用 Wire 读 WHO_AM_I（寄存器 0x75）
↓ 命中
②判为 MPU6050 系 → I2C，朝向 +π/28P 排母物理上插不进 6500
↓ 未命中
③probeSPI(候选 CS: imuCsPin / 42 / 17)不同批次 PCB 片选布线不同，逐个试
↓ 命中
④判为 MPU6500 系 → SPI，朝向 −π/2记住真正可用的 CS
↓ 都未命中
⑤imuOK = false禁止解锁 + 红灯常亮 + 长鸣

6.3 空指针防护（防崩的关键）

if (imu == nullptr || imu->status() != 0) {
    imuOK = false;
    print(TXT_IMU_UNUSABLE);   // 惯性测量单元不可用 —— 已禁止解锁
    return;
}

void readIMU() {
    if (!imuOK || imu == nullptr) return;   // ← 首行就挡掉
    ...
}
设计取舍：IMU 不可用时不让整机死掉，而是"标记不可用 + 禁止解锁"。飞机仍能连上、能看日志、能改参数 —— 现场就能判断是排母松了还是芯片坏了，而不是面对一块"插上就没反应"的板子。

6.4 朝向锁

参数 IMU_ROT_LOCK：置 1 后自动识别不再覆盖 imuRotation。跑完 ca 之后建议置 1 —— 因为自动识别是每次上电都探一遍，若某次探测失败或 WHO_AM_I 落在模糊区间，可能把已经标定好的朝向改错。

p IMU_ROT_LOCK 1

6.5 六面加速度校准（ca）：一个真实的 C++ 陷阱

六面校准的数学很简单：六个姿态覆盖每轴的 ±1g，于是

accScale = (accMax − accMin) / 2 / G      // 理想值 ≈ 1.0
accBias  = (accMax + accMin) / 2          // 理想值 ≈ 0
🐛 2026-10-18 台架实测发现的 bug：static 局部变量只初始化一次

原写法把极值累加器声明在 calibrateAccelOnce() 函数内部：
static Vector accMax(-INFINITY, ...);
static Vector accMin(INFINITY, ...);

C++ 的 static 局部变量只在第一次调用时初始化，之后再进来保留上次的值。 后果：第二次执行 ca 时，accMax/accMin 还是上一轮（甚至上电以来）的残留， accScale 完全失真 —— 实测算出 0.000257（应 ≈ 1.0）， 加速度读数随之变成 −0.86 / 0.19 / 9.19，姿态彻底不准。

修法：提升为文件级全局 accCalMax/accCalMin， 在 calibrateAccel() 开头显式重置为 ±INFINITY。

验证：修复后同样的错误操作下，比例系数从 0.000257（1e-4 量级）变成 0.0222（1e-2 量级）—— 数量级抬升 100 倍，证明累加器这次是从空集干净起步的。
⚠️ ca 的可用性缺陷：48 秒一口气跑完，人手跟不上

固件执行顺序是：打印"第 1/6 步" → pause(8) → 采样 → 打印"第 2/6 步" → pause(8) → 采样 …… 全程没有任何等待输入，约 48 秒跑完。

若操作者没能在每个 8 秒窗口内把机身翻到指定姿态，六次采样会落在同一个姿态上， accScale 塌到 1e-2 量级。这是设计缺陷，不是操作问题。

彻底解法：把 ca 拆成 ca1~ca6 六条单步命令， 每条只采一个面并等待操作者确认（当前版本尚未实施）。
坏校准的救急恢复（不用重刷固件）：
p IMU_ACC_SCALE_X 1　p IMU_ACC_SCALE_Y 1　p IMU_ACC_SCALE_Z 1
p IMU_ACC_BIAS_X 0　p IMU_ACC_BIAS_Y 0　p IMU_ACC_BIAS_Z 0

六条命令执行后姿态立刻归零（实测横滚 0.015° / 俯仰 −0.004°）。 MPU-6500 出厂精度足够直接使用，不会掉精度。
💡 别被"采样频率"误导：imu 命令打印的"采样频率"是 loopRate（主循环频率），不是 IMU 的输出速率（ODR）。
  • 校准期间 pause() 跑的是 delay(50) 慢循环 → 显示 20 Hz
  • 空闲时主循环被 waitForData() 卡住 → 显示 1 Hz
  • 正常飞行时 → 1000 Hz
这三个数值都是正常的，不要去改 configureIMU()。

七、控制回路

7.1 三层环

外环姿态环（角度 → 角速度目标）P 控制，输入横滚/俯仰角误差
↓ 角速度目标
内环角速度环（PID）含积分限幅（windup）与微分低通
↓ 力矩
混控四轴混控 → 四路油门X 型布局，油门 + 三轴力矩合成
↓
输出PWM 20 kHz → 电机含 idle 油门、饱和保护

7.2 混控方向验证（不用上机的方法）

验证混控方向有个绕不过去的坎：一旦某一路电机输出被 desaturate() 削顶 （截到 0 或 1），四路读数就失去可比性，"前侧大还是后侧大"这种比较彻底失效。

⚠️ 2026-10-18 台架实测撞到的坑：
读 mot 输出时得到
右前 1.000（削顶） / 左前 0.193 / 右后 0.077 / 左后 −0.393（削底）

这种数据既看不出俯仰、也看不出横滚，只能看出"操作者斜着压了机身"。 靠 mot 读数验证混控方向是不可行的。

正确做法：离线数学验证。工具脚本 Tools/mixer_sign_check.py 把固件里的 符号链在 Python 里原样复现，喂已知姿态看输出方向：

control.ino:82   upActual  = rotate(up, attitude)
control.ino:85   error     = rotationVectorBetween(upTarget, upActual)
vector.h:113     direction = cross(a, b)          ← a=target, b=actual
vector.h:128     return direction * angle
control.ino:87-88 ratesTarget.x/y = PID(error.x/y)   ← 增益为正，符号不变
control.ino:101-102 torqueTarget.x/y = PID(rateError)
control.ino:119-122 混控（X 型）：
    FL = T + tx − ty + tz
    FR = T − tx − ty − tz
    RL = T + tx + ty − tz
    RR = T − tx + ty + tz
姿态正确预期原理
机头下压前侧推力 > 后侧前侧往上顶 → 产生抬头力矩（跷跷板原理：想在落下那端翘起，就在那端下面顶）
机头上仰前侧推力 < 后侧后侧往上顶 → 产生低头力矩
右侧压低右侧推力 > 左侧右侧往上顶 → 产生左滚力矩
左侧压低左侧推力 > 右侧左侧往上顶 → 产生右滚力矩
✅ 验证结果（2026-10-18）：俯仰与横滚混控方向全部正确。

交叉校验：脚本算出的「右侧压低 → 右侧加推力」，与台架实测 （右倾时 右前 0.205 / 右后 0.257 > 左前 0.088 / 左后 0.134）完全吻合， 说明推演方法与固件实际行为一致、结论可信。
🔴 判据曾写反过一次，记录在此防回退：四轴 X 型的四个电机都在机身平面内， 靠相对推力差产生力矩。机头下压时是前侧加推力（把机头端顶起来）， 不是后侧加推力。写反会导致验证结论完全颠倒。

模式枚举行为

ACRO1角速度控制，摇杆给角速度目标

7.4 MANUAL_CONTROL 量程语义（重要）

协议规定 x/y/z/r 是 int16，满量程 ±1000。本工程：

controlThrottle = m.z / 1000.0f;   // z: -1000 ~ +1000 → -1 ~ +1
controlPitch    = m.x / 1000.0f;
controlRoll     = m.y / 1000.0f;
controlYaw      = m.r / 1000.0f;
台架必查：若遥控器实际发的是 0 ~ 1000（把中位当 0），则摇杆中位就已经是 0 油门、上半程才有推力，表现为"行程只有一半、且中点起跳"。
首次台架必须确认：最低杆 → z ≈ -1000，中位 → z ≈ 0，最高杆 → z ≈ +1000。用 rc 命令看归一化后的油门值。

八、安全机制

8.1 失联保护（safety.ino）

条件行为
遥控 / 地面站全部静默 1 秒缓慢下降油门
静默 10 秒油门归零 + 自动上锁
倾角超过 SF_DISARM_TILT判定翻滚，上锁
"四源全静默"的陷阱：本固件靠"是否收到控制输入"判断失联。如果你只是把遥控器放在一边不操作、也没有地面站在发心跳，1 秒后就会开始降油门。这是设计行为，不是 bug。台架测试时记得保持摇杆活动或接一个地面站。

8.2 解锁前检查

  • IMU 必须可用（imuOK）
  • 油门必须在最低位（归一化 < 0.05），否则拒绝并打印 拒绝解锁：油门不在最低位
  • 倾角不能超过阈值

8.3 指令 ACK 统一（R2）

handleMavlinkCommand() 只负责决定结果码 + 做副作用，绝不自己发 ACK；发 ACK 统一由调用方在函数返回后无条件执行：

int result = handleMavlinkCommand(&m);
mavlink_message_t ack;
mavlink_msg_command_ack_pack(..., m.command, result, ...);
sendMessage(&ack);   // ← accepted / denied / unsupported 都发

这样新增指令时结构上不可能漏发 ACK，QGC 不会卡在"正在执行"。

9.1 灯语优先级

优先级条件表现
1（最高）电压 < 3.5 V红灯 100 ms 快闪 + 蜂鸣器连续急鸣
2已连接 且 已解锁绿灯 200 ms 快闪
3已连接 且 未解锁绿灯常亮
4未连接红灯 500 ms 慢闪

9.2 音效

代号音效触发含义
'S'短鸣上电开始初始化
'D'双短鸣初始化完成 / 遥控连上就绪
'T'三短鸣解锁成功已解锁
'L'长鸣失去遥控 / IMU 不可用告警

音效语义与耀坤自研飞控 YaoKunDrone 保持一致，"短/双/三/长/急"的手感相同，用户在两套飞控之间不用重新学。

9.3 为什么蜂鸣器必须非阻塞

如果在主循环里 delay() 放音，1 kHz 的主循环会被直接打断，姿态解算跟着丢步 ⇒ 解锁瞬间就翻。这是真实踩过的坑。

所以用"状态机 + 由主循环驱动"：

  • buzzerPlay(char) 只设参数，立即返回
  • buzzerUpdate() 在主循环里推进时序（updateLED() 第一件事就是调它）
  • 只有 setup() 里那两次提示音用 runBuzzerFor(ms) 主动跑一小段（此时还没解锁，阻塞无害）

9.4 连接判据的坑

上游语义等价写法是用 mavlinkTime 判"地面站在线"，但 mavlinkTime 任何 MAVLink 帧到达都会刷新 —— 包括地面站心跳、参数请求，甚至飞机自己发出的帧被回环计数。结果就是"没接遥控也显示已连接"，灯语在骗人。

本版改用 controlTime：

const bool connected = valid(controlTime) && (t - controlTime < 1.0f);

controlTime 只在 MANUAL_CONTROL（遥控摇杆帧）到达时更新，语义上才是真正的"遥控在线"。若启用了 SBUS，readRC() 也会更新它，两条路径都对。

10.1 设计

10.2 为什么不直接把中文写进各 .ino

保留英文编译路径

10.3 怎么编英文版

// 方法一：在 flix.ino 最顶部（第一条 #include 之前）加一行
#define FLIX_LANG_EN

// 方法二：编译时传宏，不改任何文件
arduino-cli compile --build-property "compiler.cpp.extra_flags=-DFLIX_LANG_EN" ...

10.4 约定

  • 宏展开后是字符串字面量，所以写 print(TXT_XXX)，不要写 print("%s", TXT_XXX)
  • 带参数的写成"前缀宏 + 格式串"两段拼接，保证中英文各自语序自然：print(TXT_CH_SET, ch)

14.1 help 菜单只显示前半截（已修）

根因是三步凑一起才炸，单独看每一步都不像问题：

只插 UART 口看不到日志控制台走原生 USB（CDCOnBoot=cdc）改用原生 USB 口
#环节事实
①motd 是一整条 C 字符串品牌条 + 30 行命令表 = 1718 字节，print() 里 vsnprintf 后一次 Serial.print(buf) 整体写出
②ESP32-S3 原生 USB 走 HWCDC发送环形缓冲默认只有 256 字节（core 的 HWCDC.cpp 里 setTxBufferSize(256)）
③本项目设了 setTxTimeoutMs(0)写操作"绝不阻塞"——HWCDC::write() 里 xRingbufferSend 以 0 tick 超时，装不下的部分当场 break 静默丢弃

⇒ 1718 字节一次性塞进 256 字节的缓冲，只有前 ~256 字节能进；USB 中断还没来得及往主机搬， 其余 1400+ 字节全部丢掉。丢弃点正好落在品牌条末尾，所以看起来像"菜单丢了"， 而不是"打印到一半断掉"——这也是最初误判成"代码里压根没写菜单"的原因。

两处配合才修好：

  1. 扩缓冲：setupConsole() 里加 Serial.setTxBufferSize(4096)。 整份 motd 一次塞进环形缓冲，由 USB 中断异步搬给主机。主循环依旧零阻塞 （setTxTimeoutMs(0) 保持不变），飞行实时性不受影响。代价 4 KB 堆内存。
  2. 收尾补推：光扩缓冲不够——"最后一段"输出会滞留在缓冲里等下一次写入才被带走 （HWCDC 中断只在 write() 结尾重新使能）。所以 handleConsole() 命令收尾要调 consoleFlushTail(150, ' ') 补一刀：补写一个空格 （不可见、不拆行）重新使能中断，再等缓冲排空。
⚠️ 两个不能踩的坑
① 不要用 Serial.flush()：本项目 setTxTimeoutMs(0) 时， HWCDC::flush() 的 tries 一上来就是 0 → 直接走 flushTXBuffer(NULL, 0)，会把整个发送缓冲丢弃并把自己标记成"未连接"。
② 排空判定不要写 >= 4096：TX 环形缓冲是 BYTEBUF 类型， 可用空间最大值是"容量 − 1"（留 1 字节区分满/空），那个条件永远不成立， 每次都会白等满超时。改为"连续两拍可用空间不再增长"即判定排空，与容量解耦。

十五、飞行能力边界

本固件是 纯姿态自稳 + 手动油门，没有任何位置/速度传感器（无 GPS / 气压计 / 测距 / 光流）。control.ino 只有三层环（姿态 → 角速度 → 混控）。
你想要实际情况
松杆悬停不会。姿态会稳平，但会保持水平速度继续飘
松油门保持高度不会。直接掉高度（没有定高环）
低电自动降落不会降落，只有低电告警（红灯快闪 + 急鸣）
失联自动返航不会返航，只有 1 秒降油门、10 秒归零上锁
抗风姿态环能抗扰动，但会被风推走位置 —— 这是没有位置传感器的必然结果
正确的心智模型：把它当成"会自动帮你扶平的飞机"，而不是"会自动停在原地的飞机"。飞的时候手要一直在杆上。
